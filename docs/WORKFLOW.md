# Working with this repository

Day-to-day usage. For what the layout means see [STRUCTURE.md](STRUCTURE.md); for the rules that
apply to agents and the deructive `homelab:*` tasks see [../CLAUDE.md](../CLAUDE.md).

## The one rule: `DIR` is a shell variable, not a task argument

```bash
DIR=infra/oracle/vcn task plan      # correct
task plan DIR=infra/oracle/vcn      # WRONG - silently unscoped
```

Both forms are accepted and only the first one works. `.tasks/terragrunt.yml` scopes the task with
`dir: $DIR`, which is expanded from the **process environment**. Writing `DIR=...` after the task
name sets a go-task *variable* instead, which `dir: $DIR` never reads — verified on go-task 3.54.0,
where the second form runs from the repository root.

That matters more than it looks, because the command underneath is
`terragrunt <action> --all`: unscoped, it recurses over every unit in `homelab/`, `infra/`,
`prod-0/` and `prod-1/` at once. There is no guard in this repository — a bare `task apply` and a
`task apply DIR=...` both reach the whole tree.

Plan and apply the same `DIR`, always:

```bash
DIR=infra/oracle/vcn task plan
DIR=infra/oracle/vcn task apply
```

## Commands

Run `task --list-all` — the Taskfile is the source of truth, this table is a summary.

| Command | What it does |
|---|---|
| `DIR=<path> task plan` | `terragrunt plan --all` under `<path>` |
| `DIR=<path> task apply` | `terragrunt apply --all` under `<path>` |
| `DIR=<path> task destroy` | `terragrunt destroy --all` under `<path>` |
| `DIR=<path> task validate` | `terragrunt validate --all` under `<path>` |
| `DIR=<path> task outputs` | `terragrunt output` |
| `DIR=<path> task unlock -- <LOCK_ID>` | `terragrunt force-unlock` |
| `DIR=<path> task migrate-state` | `init -migrate-state -force-copy`, for bootstrap |
| `task fmt` | format all HCL |
| `task cleanup` | drop `.terragrunt-cache`, `.terraform`, generated files, lockfiles |

`--` passes the rest through to terragrunt, e.g. `DIR=... task plan -- -target=...`.

## A unit

A unit is a directory containing a `terragrunt.hcl` that includes `root.hcl` plus one wrapper from
`_common/`. The wrapper carries the module `source`; the unit carries only `dependency` blocks and
`inputs`. `DIR` points at a unit, or at a directory above several of them when you deliberately
want `--all` to sweep that subtree.

## Before the first run

```bash
mise trust && mise install
cp .env.example .env
```

`mise.toml` pins the CLI versions the tasks expect — `opentofu` (binary `tofu`, not `terraform`),
`terragrunt`, `kubectl`, `talosctl`, `hcloud`, `jq`. `.env` holds the credentials, including
`TF_HTTP_PASSWORD` (a GitLab Personal Access Token) for the remote state.

## State

Remote state lives in the GitLab Terraform State Registry; the backend block is generated by
`root.hcl`, so no unit configures it. One state per unit path.

## Treat as dangerous

`destroy`, `unlock` and `migrate-state` exist for real incident and bootstrap scenarios, not for
routine use. `unlock` releases a lock another apply may still be holding; `migrate-state` moves
state between backends. Both are easy to run against the wrong `DIR`.

The `homelab:*` tasks provision the physical node: `homelab:flash` writes a disk image with `dd`,
`homelab:config` dumps live cluster secrets into a git-ignored file, and `homelab:config-server`
serves that file unauthenticated on the LAN. Read [../CLAUDE.md](../CLAUDE.md) before running any
of them.
